# 第1章-03：リソースとアーキテクチャ

---

## 1. リソースとは何か

Web の世界では、URI で識別できる **あらゆるもの** を「リソース（Resource）」と呼びます。

```
https://example.com/users/42
```

このURIが指す「ID が42のユーザー」がリソースです。

リソースは実体（データ、文書、サービス）を問いません。

| リソースの例 | URI の例 |
|-------------|---------|
| 商品情報 | `https://shop.example.com/products/100` |
| ユーザーアカウント | `https://api.example.com/users/42` |
| 天気予報 | `https://weather.example.com/tokyo/today` |
| 画像ファイル | `https://cdn.example.com/images/photo.jpg` |
| 検索結果 | `https://search.example.com/results?q=web` |

---

## 2. リソースと表現（Representation）

重要な概念として、**リソースそのものと、リソースの表現は別物** です。

```
リソース：「ID が42のユーザー」という概念・実体

表現①（HTML）：   <h1>Kazuki Matsuo</h1>
表現②（JSON）：   {"id": 42, "name": "Kazuki Matsuo"}
表現③（XML）：    <user><id>42</id><name>Kazuki Matsuo</name></user>
```

同一リソースを異なる形式で表現できます。
どの表現を返すかはサーバーとクライアントが交渉して決めます（コンテントネゴシエーション）。

この「リソースと表現の分離」は REST アーキテクチャの核心概念です。

---

## 3. Web のアーキテクチャ：クライアント・サーバー

Web の基本的なアーキテクチャは **クライアント・サーバーモデル** です。

```
┌─────────────┐         HTTP          ┌─────────────┐
│   クライアント   │  ──────────────>  │   サーバー    │
│（ブラウザ等）  │  <──────────────  │（Web サーバー）│
└─────────────┘    リクエスト/レスポンス   └─────────────┘
```

### クライアントの役割
- ユーザーの操作を受け付ける
- HTTP リクエストを生成してサーバーに送る
- サーバーからのレスポンスを解析して表示する

### サーバーの役割
- クライアントからのリクエストを受け付ける
- リソースを探す・生成する
- HTTP レスポンスをクライアントに返す

---

## 4. 多層アーキテクチャ

実際の Web システムは単純なクライアント・サーバーだけでなく、
複数の層（レイヤー）で構成されます。

```
クライアント（ブラウザ）
      ↕ HTTP
CDN / ロードバランサー
      ↕ HTTP
Web サーバー（Nginx / Apache）
      ↕
アプリケーションサーバー（Rails / Spring / etc.）
      ↕
データベースサーバー（MySQL / PostgreSQL / etc.）
```

HTTP の視点では、クライアントはどの層と通信しているか意識しません。
**URI で指定したリソースを取得できれば**、どんな内部構成でもよいのです。

この透過性（透明性）が Web の柔軟性を生んでいます。

---

## 5. プロキシとゲートウェイ

クライアントとサーバーの間には、中継役が入ることがあります。

### プロキシ（Proxy）

クライアント側の代理として動作するサーバーです。

```
クライアント → プロキシ → サーバー
```

用途：
- キャッシュ（同じリクエストを毎回サーバーに送らない）
- アクセス制御（特定サイトへのアクセスを遮断）
- ログ収集（通信内容を記録する）

### リバースプロキシ

サーバー側の代理として動作します。

```
クライアント → リバースプロキシ → 複数のサーバー
```

用途：
- ロードバランシング（負荷分散）
- SSL 終端（HTTPS の暗号化処理を集約）
- キャッシュ

Nginx を Web サーバーの前段に置いてリバースプロキシとして使う構成が一般的です。

### ゲートウェイ

異なるプロトコルを橋渡しするサーバーです。
たとえば、HTTP のリクエストを受け取り、内部では独自プロトコルで処理する場合に使います。

---

## 6. ステートレス性

HTTP の重要な特性として **ステートレス（Stateless）** があります。

「状態を持たない」という意味で、各 HTTP リクエストは完全に独立しています。
サーバーは前回のリクエストのことを覚えていません。

```
リクエスト1: GET /users/42      → サーバーが応答
リクエスト2: GET /products/10   → サーバーは「リクエスト1があった」を知らない
```

### ステートレスのメリット

- **スケーラビリティ**：どのサーバーがリクエストを処理してもよい（ロードバランシングが容易）
- **シンプルさ**：サーバーがセッション情報を管理する必要がない
- **信頼性**：サーバーが落ちても、別のサーバーで再開できる

### ステートレスのデメリット

- **リクエストが大きくなる**：毎回必要な情報（認証情報など）を送る必要がある
- **ユーザーの連続した操作を管理しにくい**

このデメリットを補うために Cookie やセッションが使われますが、
それは HTTP の上に乗っかった仕組みであり、HTTP 自体はステートレスのままです。

---

## 7. Web の進化：静的から動的へ

### 静的 Web（初期の Web）

最初の Web は主に静的な HTML ファイルを配信するものでした。

```
リクエスト → サーバーが HTML ファイルをそのまま返す
```

### 動的 Web（CGI の登場）

CGI（Common Gateway Interface）により、リクエストに応じて動的に HTML を生成できるようになりました。

```
リクエスト → サーバーがプログラムを実行 → HTML を生成して返す
```

### Web アプリケーション（現在）

現在は複雑なビジネスロジックを持つ Web アプリケーションが主流です。

```
リクエスト → Web サーバー → アプリサーバー → DB → レスポンス生成
```

### SPA（Single Page Application）

近年は JavaScript がサーバーから JSON を取得し、
ブラウザ側でページを動的に構築する SPA が普及しています。

```
初回: HTML/CSS/JS を取得
以降: API（JSON）のみをやり取り → JS がページを更新
```

---

## まとめ

- リソース：URI で識別できる Web 上のあらゆるもの
- 表現：リソースを具体的な形式（HTML・JSON・XML）で表したもの。リソース自体とは別
- クライアント・サーバー：Web の基本アーキテクチャ
- ステートレス：各リクエストは独立。スケーラビリティのために重要な設計
- プロキシ/リバースプロキシ：キャッシュ・負荷分散・セキュリティのために使われる中継役
