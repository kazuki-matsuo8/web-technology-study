# 第5章-02：REST の6つの制約

---

## 1. REST の制約とは

フィールディングは REST を「6つの制約（Constraints）の組み合わせ」として定義しました。

これらの制約に従うことで、スケーラブルで相互運用可能なシステムが実現します。

```
1. クライアント・サーバー
2. ステートレス
3. キャッシュ
4. 統一インターフェース（最も重要）
5. 階層化システム
6. コードオンデマンド（任意）
```

---

## 2. 制約1：クライアント・サーバー（Client-Server）

クライアントとサーバーを **分離** します。

```
クライアント（UI を担当）          サーバー（データ・ロジックを担当）
   ↕ HTTP（統一されたインターフェース）
```

### この制約のメリット

- **関心の分離**：UI の変更がサーバーに影響しない。サーバーの変更が UI に影響しない
- **独立した進化**：クライアントとサーバーを別々に開発・デプロイできる
- **多様なクライアント**：同じサーバーに対して、ブラウザ・スマホアプリ・CLI ツール等が接続できる

---

## 3. 制約2：ステートレス（Stateless）

各リクエストは **完全に独立** していなければなりません。
サーバーはリクエストに必要な情報をすべてリクエスト自体から得られる必要があります。

```
良い例（ステートレス）:
GET /users/42 HTTP/1.1
Authorization: Bearer eyJ...  ← 認証情報を毎回送る

悪い例（ステートフル）:
GET /users/42 HTTP/1.1
← 「さっきログインしたから覚えているはず」という前提
```

### この制約のメリット

- **可視性**：リクエスト1つ見るだけで全情報がわかる
- **信頼性**：サーバーが落ちて別サーバーに切り替わっても問題なし
- **スケーラビリティ**：どのサーバーがリクエストを処理してもよい（ロードバランシングが容易）

### この制約のデメリット

- 毎回認証情報など必要情報を送る必要があり、リクエストが大きくなる
- セッション管理（ログイン状態の維持）がやや複雑になる

---

## 4. 制約3：キャッシュ（Cacheable）

レスポンスは **キャッシュ可能かどうか** を明示しなければなりません。

```http
Cache-Control: max-age=3600     ← 1時間キャッシュ可能
Cache-Control: no-store         ← キャッシュ不可
```

### この制約のメリット

- **パフォーマンス向上**：同じリクエストをサーバーに送らなくてよい
- **スケーラビリティ**：サーバー負荷を軽減できる
- **ユーザー体験**：レスポンスが速くなる

### この制約のデメリット

- キャッシュが古いデータを返してしまうと、データが stale（陳腐化）になる

---

## 5. 制約4：統一インターフェース（Uniform Interface）

REST の **最も重要な制約** です。
すべてのリソースに対して、同じインターフェースでアクセスします。

統一インターフェースは4つのサブ制約で構成されます。

### サブ制約1：リソースの識別

すべてのリソースは URI で識別される。

```
/users/42     ← リソース: ID が42のユーザー
/orders/100   ← リソース: ID が100の注文
```

### サブ制約2：表現によるリソース操作

クライアントはリソースの「表現（Representation）」を使ってリソースを操作する。

```http
PUT /users/42 HTTP/1.1
Content-Type: application/json

{"name": "New Name", "email": "new@example.com"}
← この JSON がリソースの新しい表現
```

### サブ制約3：自己記述メッセージ

メッセージは自分自身を説明する情報を含んでいる。
受信者がメッセージを解釈するのに必要な情報がすべてメッセージ内にある。

```http
HTTP/1.1 200 OK
Content-Type: application/json   ← これを見ればボディが JSON とわかる

{"id": 42, "name": "Kazuki"}
```

### サブ制約4：HATEOAS

HATEOAS（Hypermedia As The Engine Of Application State）は
「アプリケーション状態のエンジンとしてのハイパーメディア」という意味です。

レスポンスに **次のアクションへのリンク** を含めることで、
クライアントはサーバーの API 構造を事前に知らなくても操作できます。

```json
{
  "id": 42,
  "name": "Kazuki",
  "balance": 5000,
  "_links": {
    "self": {"href": "/users/42", "method": "GET"},
    "update": {"href": "/users/42", "method": "PUT"},
    "delete": {"href": "/users/42", "method": "DELETE"},
    "orders": {"href": "/users/42/orders", "method": "GET"},
    "deposit": {"href": "/users/42/deposits", "method": "POST"}
  }
}
```

HATEOAS が実現されると：
- クライアントは最初の URI だけ知っていればよい
- API の変更に柔軟に対応できる
- ドキュメントなしでも API を探索できる

ただし、HATEOAS は実装コストが高く、実際の API で完全実装されることは少ないです。

---

## 6. 制約5：階層化システム（Layered System）

クライアントはサーバーに直接接続しているか、中間サーバー経由かを意識しない。

```
クライアント → ロードバランサー → Web サーバー → アプリサーバー → DB
```

クライアントからは「どこかのサーバーと通信している」ようにしか見えません。

### この制約のメリット

- **スケーラビリティ**：サーバーを増やしても（ロードバランシング）クライアントに影響なし
- **セキュリティ**：中間層でセキュリティチェック、暗号化できる
- **キャッシュ**：中間層（CDN・プロキシ）でキャッシュできる

---

## 7. 制約6：コードオンデマンド（Code-On-Demand）【任意】

これのみ任意の制約です。

サーバーがクライアントに **実行可能なコード（スクリプト）を送る** ことができます。

```html
<script src="https://cdn.example.com/app.js"></script>
```

JavaScript がそのまま実例です。
サーバーが JS ファイルを返し、ブラウザがそれを実行します。

### この制約のメリット

- クライアントの機能をサーバー側から拡張できる

### この制約のデメリット

- クライアントが不明なコードを実行するセキュリティリスク

---

## 8. 6つの制約のまとめ

| 制約 | 概要 | 主なメリット |
|------|------|------------|
| クライアント・サーバー | UI とデータを分離 | 独立した進化・多様なクライアント |
| ステートレス | リクエスト間で状態を持たない | スケーラビリティ・信頼性 |
| キャッシュ | キャッシュ可否を明示 | パフォーマンス向上 |
| 統一インターフェース | 共通の操作方法 | 相互運用性・シンプルさ |
| 階層化システム | 中間層の存在を透過 | セキュリティ・スケーラビリティ |
| コードオンデマンド（任意）| 実行可能コードの配信 | クライアント機能の拡張 |

これらを組み合わせることで、スケーラブルで長期的に進化可能な Web システムが実現します。

---

## 9. なぜ多くの API が「厳密な REST」ではないか

HATEOAS を完全実装する API は非常に少ないです。
理由は実装コストと実用性のバランスです。

現実の多くの「REST API」は：
- URI でリソースを識別する ○
- HTTP メソッドを正しく使う ○
- ステータスコードを正しく使う ○
- JSON を返す ○
- HATEOAS を実装する △（多くが省略）

これを「REST レベル」として分類する Richardson Maturity Model（RMM）という
モデルもあります。

```
Level 0: HTTP をただのトンネルとして使う（SOAP など）
Level 1: リソースの URI を使う
Level 2: HTTP メソッドを正しく使う
Level 3: HATEOAS（ハイパーメディア）を使う  ← 真の REST
```

多くの実用的な API は Level 2 です。

---

## まとめ

REST の6つの制約：
1. クライアント・サーバー：UI とデータの分離
2. ステートレス：各リクエストは完全に独立
3. キャッシュ：キャッシュ可否を明示
4. 統一インターフェース：共通の操作方法（最重要）
   - リソースの URI 識別
   - 表現によるリソース操作
   - 自己記述メッセージ
   - HATEOAS
5. 階層化システム：中間層の透過
6. コードオンデマンド（任意）：実行可能コードの配信
