# 第6章-01：HTTPS とセキュリティ

---

## 1. HTTPS とは

HTTPS（HyperText Transfer Protocol **Secure**）は、
HTTP 通信を **TLS（Transport Layer Security）** で暗号化したものです。

```
HTTP  + TLS = HTTPS
（通信）（暗号化）
```

現在、Web サイトの標準は HTTPS です。
HTTP（非暗号化）でのサービス提供は時代遅れとなっています。

---

## 2. なぜ HTTPS が必要か

HTTP では通信内容が平文（暗号化なし）で送受信されます。

```
HTTP の通信（平文）:

クライアント → 「GET /login HTTP/1.1 ... password=myPassword」
                          ↑ ネットワーク上を平文で流れる
                          ↑ 盗聴すれば丸見え

HTTPS の通信（暗号化）:

クライアント → 「（暗号化されたデータ）」
                          ↑ 盗聴しても解読不能
```

### HTTPS が防ぐ攻撃

| 攻撃 | 説明 |
|------|------|
| 盗聴 | 通信内容が読まれる（パスワード・クレカ番号の漏洩）|
| 改ざん | 通信内容を途中で書き換えられる（広告挿入・マルウェア注入）|
| なりすまし | 偽のサーバーに誘導される（フィッシング）|

---

## 3. TLS の仕組み

### TLS の3つの機能

1. **暗号化**：通信内容を第三者が読めないようにする
2. **完全性**：通信内容が改ざんされていないことを保証する
3. **認証**：接続先が本物のサーバーであることを確認する

### TLS ハンドシェイク（接続確立の流れ）

```
クライアント                              サーバー
   |                                       |
   |  ClientHello                          |
   |  （使用可能な暗号スイート・乱数）         |
   |  ─────────────────────────────────>   |
   |                                       |
   |  ServerHello                          |
   |  （選択した暗号スイート・乱数）           |
   |  Certificate（サーバー証明書）           |
   |  <─────────────────────────────────   |
   |                                       |
   |  （証明書の検証：CA の署名を確認）        |
   |                                       |
   |  （セッションキーを確立）                 |
   |  Finished                             |
   |  ─────────────────────────────────>   |
   |                                       |
   |            Finished                   |
   |  <─────────────────────────────────   |
   |                                       |
   |  (以降は暗号化された HTTP 通信)         |
```

## 4. デジタル証明書

HTTPS では、**デジタル証明書（TLS 証明書）** がサーバーの身元を保証します。

### 証明書の役割

```
「私は example.com のサーバーです」という主張を
認証局（CA: Certificate Authority）が保証する。
```

### 証明書に含まれる情報

- ドメイン名（コモンネーム）
- 証明書の有効期限
- 発行者（CA）
- 公開鍵
- CA の署名

### 証明書チェーン

証明書は「信頼の連鎖（Chain of Trust）」で成り立っています。

```
ルート CA（ブラウザに事前にインストール）
    ↓ 信頼を委任
中間 CA
    ↓ 信頼を委任
サーバー証明書（example.com）
```

ブラウザはルート CA を信頼しており、そこから連鎖して
サーバー証明書を信頼するかどうかを判断します。

### 証明書の種類

| 種類 | 確認内容 | 用途 |
|------|---------|------|
| DV（Domain Validation）| ドメイン所有者確認のみ | 一般的なサイト |
| OV（Organization Validation）| 組織の実在確認 | 企業サイト |
| EV（Extended Validation）| 厳格な組織確認 | 金融・ECサイト |

### Let's Encrypt

無料で自動的に DV 証明書を発行してくれる認証局です。
HTTPS の普及に大きく貢献しています。

```bash
# Certbot で Let's Encrypt 証明書を取得する例
certbot certonly --webroot -w /var/www/html -d example.com
```

## 5. 公開鍵暗号と共通鍵暗号

TLS は2種類の暗号方式を組み合わせて使っています。

### 共通鍵暗号（対称暗号）

暗号化と復号に **同じ鍵** を使います。

```
送信者: データ + 共通鍵 → 暗号文
受信者: 暗号文 + 共通鍵 → データ
```

高速ですが「どうやって鍵を安全に共有するか」という問題があります。

### 公開鍵暗号（非対称暗号）

**公開鍵（誰でも知ってよい）** と **秘密鍵（自分だけが持つ）** のペアを使います。

```
公開鍵で暗号化 → 秘密鍵でのみ復号できる
秘密鍵で署名   → 公開鍵で検証できる（なりすまし防止）
```

鍵の共有問題が解決しますが、処理が遅い。

### TLS での使い分け

```
TLS ハンドシェイク時:
→ 公開鍵暗号を使って「セッションキー（共通鍵）」を安全に交換

データ転送時:
→ 共通鍵（セッションキー）で高速に暗号化
```

## 6. HSTS（HTTP Strict Transport Security）

一度 HTTPS でアクセスしたサイトに、次回から **強制的に HTTPS でアクセスする** 仕組みです。

```http
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
```

| パラメーター | 意味 |
|------------|------|
| `max-age=31536000` | 1年間 HTTPS を強制 |
| `includeSubDomains` | サブドメインも対象 |
| `preload` | ブラウザの HSTS プリロードリストに登録 |

HSTS プリロードリストに登録されたドメインは、
一度もアクセスしていなくても最初から HTTPS が強制されます。

---

## 7. 証明書の確認

ブラウザで証明書の情報を確認できます。

```
アドレスバーの鍵アイコン → 「接続が保護されています」→ 証明書の詳細を表示
```

`curl` での確認：

```bash
# 証明書の詳細を表示
curl -v https://example.com/ 2>&1 | grep -A 20 "Certificate"

# 証明書の有効期限を確認
echo | openssl s_client -connect example.com:443 2>/dev/null | openssl x509 -noout -dates
```

## 8. よくある HTTPS 関連の問題

### 混在コンテンツ（Mixed Content）

HTTPS ページから HTTP のリソース（画像・JS・CSS）を読み込んでいる状態です。

```html
<!-- 混在コンテンツ（NG）-->
<!-- HTTPS ページなのに HTTP で画像を読み込んでいる -->
<img src="http://cdn.example.com/image.jpg">

<!-- 修正後（OK）-->
<img src="https://cdn.example.com/image.jpg">
<!-- またはプロトコル相対 URL -->
<img src="//cdn.example.com/image.jpg">
```

ブラウザは混在コンテンツをブロックするため、画像が表示されないなどの問題が起きます。

---

## まとめ

- HTTPS = HTTP + TLS（暗号化）
- TLS は「暗号化」「完全性」「認証」の3機能を提供
- デジタル証明書が「本物のサーバー」を保証する。CA（認証局）が署名
- TLS ハンドシェイクで共通鍵を安全に共有し、以降の通信を高速に暗号化
- HSTS で強制的に HTTPS を使わせる
- Let's Encrypt で無料・自動で証明書が取得できる
- 現代の Web では HTTPS は必須
