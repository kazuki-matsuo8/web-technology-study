# 第6章-03：現代の Web アーキテクチャ

---

## 1. Web アーキテクチャの変遷

### 第1世代：静的 Web（1991〜）

```
ブラウザ → HTTP GET → サーバー → HTML ファイルをそのまま返す
```

サーバーはファイルを返すだけ。コンテンツは変わらない。

### 第2世代：動的 Web・CGI（1993〜）

```
ブラウザ → HTTP → Web サーバー → CGI スクリプト → 動的 HTML 生成
```

PHP・Perl などでリクエストごとに HTML を生成。
動的なコンテンツが可能になった。

### 第3世代：Web アプリケーション（2000〜）

```
ブラウザ → HTTP → アプリサーバー（MVC フレームワーク）→ DB
```

Rails・Django・Spring などの MVC フレームワークが普及。
複雑なビジネスロジックを持つアプリが構築できるようになった。

### 第4世代：SPA + API（2010〜）

```
初回: ブラウザ → HTML/CSS/JS を取得
以降: JavaScript → REST API（JSON）→ 画面を動的に更新
```

React・Vue・Angular などの SPA フレームワークが普及。
API とフロントエンドが明確に分離された。

### 第5世代：マイクロサービス・クラウドネイティブ（2015〜）

```
ブラウザ → API Gateway → マイクロサービス群（各独立した小さなサービス）
```

---

## 2. SPA（Single Page Application）

### SPA の仕組み

```
① 最初に HTML・CSS・JS をすべて一括でダウンロード

② 以降はページ遷移なし
   ユーザーの操作 → JavaScript が DOM を操作 → 見た目が変わる
   必要なデータは API（JSON）で非同期取得

③ URL は変わるが、実際のページ遷移は起きない（History API で URL を更新）
```

### SPA のメリット

- **ユーザー体験が良い**：ページ全体の再読み込みなしに画面が更新される
- **フロントエンドとバックエンドの完全分離**：それぞれ独立して開発・デプロイできる
- **サーバー負荷が軽い**：サーバーは JSON を返すだけ。HTML の生成が不要

### SPA のデメリット

- **初回ロードが遅い**：大きな JS ファイルをダウンロードする必要がある
- **SEO が難しい**：JavaScript を実行しないとコンテンツが表示されない（対策：SSR）
- **状態管理が複雑**：クライアントサイドの状態管理が必要（Redux 等）

---

## 3. SSR（Server-Side Rendering）と SSG（Static Site Generation）

SPA の SEO・初回ロード問題を解決するアプローチです。

### SSR（サーバーサイドレンダリング）

```
リクエスト → サーバーが JavaScript を実行して HTML を生成 → 返す
```

- 検索エンジンが HTML を読める
- 初回表示が速い
- サーバーに処理負荷がかかる

Next.js（React）・Nuxt.js（Vue）などが SSR をサポートします。

### SSG（静的サイト生成）

```
ビルド時 → すべてのページを HTML として生成 → CDN に配置
```

- 高速（CDN から HTML をそのまま返す）
- セキュリティが高い（サーバーに動的処理がない）
- 動的なコンテンツには不向き

Gatsby・Hugo・Jekyll などが SSG ツールです。

### ISR（Incremental Static Regeneration）

SSG と SSR のハイブリッドです。

```
静的ページを配信しつつ、バックグラウンドで定期的に再生成する
```

Next.js が実装しています。

## 4. マイクロサービスアーキテクチャ

### モノリシックアーキテクチャ（従来）

```
┌────────────────────────────────┐
│          モノリシックアプリ      │
│  ユーザー管理 │ 注文管理 │ 在庫  │
│  支払い処理  │ 通知    │ 検索  │
└────────────────────────────────┘
                  ↕
              データベース
```

すべてが1つのアプリケーション。デプロイが簡単だが大規模になると管理が困難。

### マイクロサービスアーキテクチャ

```
          API Gateway
         /     |     \
        ↓      ↓      ↓
  ユーザー  注文    支払い
  サービス  サービス  サービス
    ↕        ↕        ↕
   DB       DB       DB
```

機能ごとに独立した小さなサービスに分割。
各サービスが独立してデプロイ・スケールできます。

### サービス間通信

| 方式 | プロトコル | 用途 |
|------|-----------|------|
| 同期通信 | HTTP REST / gRPC | リアルタイムで返答が必要な場合 |
| 非同期通信 | メッセージキュー（RabbitMQ / Kafka）| 返答を待たなくてよい処理 |

## 5. CDN（Content Delivery Network）

世界中に分散したサーバーにコンテンツをキャッシュし、
ユーザーに最も近いサーバーからコンテンツを返します。

```
東京のユーザー → 東京 CDN サーバー → 近いのでレスポンスが速い
ニューヨークのユーザー → NY CDN サーバー → 近いのでレスポンスが速い

（オリジンサーバー（本来のサーバー）は1箇所でよい）
```

CDN を使うことで：
- コンテンツの配信が高速になる
- オリジンサーバーへの負荷が軽減される
- DDoS 攻撃への耐性が上がる

## 6. WebSocket

HTTP は「リクエスト→レスポンス」の1回のやり取りです。
サーバーからクライアントにデータをプッシュしたい場合（チャット・リアルタイム通知等）
は不向きです。

**WebSocket** は、クライアントとサーバーが **双方向・持続的な接続** を確立する仕組みです。

```
HTTP でアップグレードリクエスト:
GET / HTTP/1.1
Upgrade: websocket

→ HTTP/1.1 101 Switching Protocols
  Upgrade: websocket

（以降は WebSocket プロトコルで双方向通信）

クライアント → サーバー: "Hello"
サーバー → クライアント: "World"（サーバーから能動的に送信可能）
```

用途：
- チャットアプリ
- リアルタイム通知
- ゲーム
- 株価・スポーツスコアのリアルタイム更新

## 7. GraphQL の実際

REST の課題を解決するクエリ言語です。

### REST の問題：オーバーフェッチとアンダーフェッチ

```
オーバーフェッチ：必要以上のデータを取得してしまう
GET /users/42
→ {"id": 42, "name": "Kazuki", "email": "...", "age": 21, "address": {...}}
  名前だけ必要なのに全部取得する

アンダーフェッチ：必要なデータを取得するために複数回リクエストが必要
GET /users/42           → ユーザー情報取得
GET /users/42/orders    → 注文情報取得
GET /orders/100/items   → 注文明細取得
3回のリクエストが必要
```

### GraphQL の解決策

```graphql
query {
  user(id: 42) {
    name         # 名前だけほしい
    orders {
      id
      items {
        productName
        quantity
      }
    }
  }
}
```

1回のリクエストで、必要なデータだけ取得できます。

## 8. Web の未来

### HTTP/3（QUIC）

UDP ベースの新しい HTTP プロトコル。
接続確立が高速で、パケットロスの影響を受けにくい。

### Edge Computing

ユーザーに近いエッジサーバーでコードを実行。
CDN の進化形で、動的処理も低レイテンシーで実行可能。

Cloudflare Workers・Vercel Edge Functions などが実例。

### Web Components

ブラウザネイティブのコンポーネント機能。
特定のフレームワークに依存しない再利用可能な UI コンポーネント。

### WebAssembly（Wasm）

C・C++・Rust などで書かれたコードをブラウザで実行できる仕組み。
JavaScript より高速な処理が可能。

## まとめ

| 時代 | アーキテクチャ | 特徴 |
|------|-------------|------|
| 1990s | 静的 Web | ファイルをそのまま返す |
| 2000s | 動的 Web | サーバーで HTML を生成 |
| 2010s | SPA + REST API | フロント・バック分離 |
| 現在 | マイクロサービス・クラウドネイティブ | 機能ごとの独立したサービス |

重要な現代の技術：
- SPA：React・Vue・Angular でクライアントサイドレンダリング
- SSR・SSG：SEO と初回ロードを改善
- CDN：地理的に分散したキャッシュで高速配信
- WebSocket：サーバーからのプッシュ通信
- GraphQL：必要なデータだけ柔軟に取得
- HTTP/3：QUIC ベースの次世代 HTTP
