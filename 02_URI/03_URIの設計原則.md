# 第2章-03：URI の設計原則

---

## 1. URI 設計がなぜ重要か

URI は Web サービスの **公開 API の一部** です。
一度公開した URI を変更すると：

- 外部からのリンクが壊れる
- ユーザーのブックマークが壊れる
- 検索エンジンの評価がリセットされる

URI は **変わらないこと** が非常に重要です。
したがって、最初の設計を慎重に行う必要があります。

---

## 2. 良い URI の条件

### 条件1：わかりやすい

URI を見ただけで、何のリソースかが推測できます。

```
悪い例: https://example.com/cgi-bin/user.php?action=view&uid=42&mode=2
良い例: https://example.com/users/42
```

良い URI は、エンジニアでない人でも「ユーザーのページ」だとわかります。

### 条件2：変わらない

リソースが存在する限り、URI は変わらないべきです。

```
悪い設計（変わりやすい）:
https://example.com/2026/04/20/blog-post-title.html
→ 日付に依存。カテゴリー変更、タイトル修正でURIが変わる

良い設計（安定している）:
https://example.com/posts/12345
→ ID で識別。タイトル変更・カテゴリー変更の影響を受けない
```

### 条件3：リソースを表している

URI はリソース（名詞）を表すべきで、操作（動詞）を表すべきではありません。

```
悪い例（操作が URI に入っている）:
https://example.com/getUser
https://example.com/deletePost/5
https://example.com/createOrder

良い例（リソースが URI に入っている）:
https://example.com/users    → ユーザー一覧（リソース）
https://example.com/posts/5  → ID が5の投稿（リソース）
https://example.com/orders   → 注文一覧（リソース）
```

操作は HTTP メソッド（GET・POST・PUT・DELETE）で表現します。

### 条件4：階層構造が意味を持つ

パスの階層がリソースの関係性を表しています。

```
/users             → 全ユーザー
/users/42          → ID が42のユーザー
/users/42/orders   → ID が42のユーザーの注文
/users/42/orders/7 → ID が42のユーザーの注文 ID が7のもの
```

親子関係をパスの階層で表現することで、直感的に理解できます。

---

## 3. URI 設計のアンチパターン

### アンチパターン1：拡張子でリソースを識別する

```
悪い例:
/user.php   → PHP で実装されていることが漏れる
/data.aspx  → ASP.NET であることが漏れる
/show.cgi   → CGI であることが漏れる
```

実装の詳細（どの言語・フレームワークで作ったか）を URI に含めると、
実装を変更したときに URI が変わってしまいます。

```
良い例:
/users/42   → 実装に依存しない
```

### アンチパターン2：セッション ID を URI に含める

```
悪い例:
/users?session=abc123xyz789
```

セッション ID は毎回変わるため、URI がリソースを一意に識別できなくなります。
また、セッション ID が URL に含まれると、ブラウザの履歴・ログに残りセキュリティ上危険です。

### アンチパターン3：行為を URI に含める

```
悪い例:
/login
/logout
/addToCart
/deleteUser/42
```

HTTP メソッドで操作を表現できるのに、URI に動詞を含めるのは冗長です。

```
良い例:
POST   /sessions         → ログイン（セッション作成）
DELETE /sessions/current → ログアウト（セッション削除）
POST   /cart/items       → カートに追加
DELETE /users/42         → ユーザー削除
```

### アンチパターン4：URI が長すぎる・複雑すぎる

```
悪い例:
/api/v1/system/users/registered/active/profile/settings/notifications
```

階層が深すぎると、人間が覚えにくく、タイプミスも増えます。
通常3〜4階層程度が限度です。

---

## 4. URI の設計パターン

### 一覧と個別リソース

```
GET  /users      → ユーザー一覧
GET  /users/42   → ID が42のユーザー
POST /users      → ユーザー新規作成
```

### 子リソース

```
GET  /users/42/posts      → ID が42のユーザーの投稿一覧
GET  /users/42/posts/7    → 投稿 ID が7のもの
POST /users/42/posts      → 新規投稿作成
```

### クエリパラメーターの使い方

階層で表せない絞り込み・ソートなどはクエリパラメーターを使います。

```
/users?role=admin              → 管理者のみ絞り込み
/users?sort=created_at&order=desc  → 作成日の降順でソート
/users?page=2&per_page=20     → ページネーション
/search?q=Web技術              → 検索
```

## 5. URI のバージョニング

API を公開する際、将来の変更に備えてバージョンを含める方法があります。

### URI にバージョンを含める（よく使われる）

```
https://api.example.com/v1/users
https://api.example.com/v2/users
```

メリット：わかりやすい。古いバージョンと新しいバージョンを並行して動かせる。
デメリット：URI 設計の原則（変わらないこと）に反する。

### ヘッダーでバージョンを指定する（REST 的に正しい）

```
GET /users HTTP/1.1
Accept: application/vnd.example.v2+json
```

メリット：URI が変わらない。
デメリット：わかりにくい。ブラウザで試しにくい。

実務では URI にバージョンを含める方法が広く使われています。

---

## 6. URI 設計のチェックリスト

設計した URI を評価するときの確認項目です。

```
□ URI を見てリソースが何かわかるか
□ 実装の詳細（言語・フレームワーク・ファイル名）が含まれていないか
□ 不必要に長くなっていないか
□ 操作（動詞）ではなくリソース（名詞）を表しているか
□ 階層構造がリソースの関係を正しく表しているか
□ 将来変更が予想される情報（日付・カテゴリー名等）が含まれていないか
□ セッション ID などの一時的な情報が含まれていないか
```

---

## まとめ

良い URI の3条件：
1. わかりやすい（見ただけでリソースがわかる）
2. 変わらない（実装の詳細に依存しない）
3. リソースを表す（動詞ではなく名詞）

URI 設計の基本：
- パス階層でリソースの親子関係を表現する
- 操作は HTTP メソッドで表現し、URI に含めない
- 拡張子や実装詳細を URI に含めない
- 一覧は複数形、個別は ID で区別する（`/users`・`/users/42`）
