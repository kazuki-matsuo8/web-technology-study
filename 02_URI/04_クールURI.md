# 第2章-04：クール URI

---

## 1. クール URI とは

**「クール URI は変わらない（Cool URIs don't change）」**

これは W3C の創始者ティム・バーナーズ＝リーが1998年に書いたエッセイの題名です。
Web の設計哲学として非常に重要な考え方です。

[原文: https://www.w3.org/Provider/Style/URI]

---

## 2. なぜ URI は変わってはいけないのか

### リンクが切れる

Web はハイパーリンクで結びついています。
URI が変わると、そのリソースへのリンクがすべて無効になります。

```
他のサイト A → https://example.com/blog/2024/web-basics
             ×（404 Not Found になる）
```

リンク切れは Web の価値を損ないます。

### ユーザー体験が悪化する

ブックマークや検索エンジンからアクセスしたとき、
404 ページが表示されると体験が悪くなります。

### SEO への影響

検索エンジンはページを URI で管理しています。
URI が変わると、それまで蓄積した検索評価がリセットされます。

---

## 3. URI が変わる原因と対策

### 原因1：技術的な実装を URI に含める

```
悪い例:
/cgi-bin/user.pl?id=42
→ CGI から Flask に移行したら URI が変わる

対策:
/users/42
→ 実装に依存しない URI にする
```

### 原因2：組織構造を URI に反映する

```
悪い例:
/department/sales/staff/yamamoto
→ 部署が再編されたら URI が変わる

対策:
/staff/yamamoto
→ 組織に依存しない URI にする
```

### 原因3：コンテンツの属性を URI に含める

```
悪い例:
/topics/web/2024/article-title.html
→ カテゴリーが変わった、タイトルが変わった → URI が変わる

対策:
/articles/12345
→ 変わらない ID で識別する
```

### 原因4：ファイルの拡張子を含める

```
悪い例:
/document.html
→ PDF に変換したら /document.pdf になる

対策:
/document
→ 実際の形式はコンテントネゴシエーションで決める
```

---

## 4. URI を変えなければならないときの対処

それでも URI を変更しなければならない場合は、
**リダイレクト** で古い URI から新しい URI へ誘導します。

```
HTTP/1.1 301 Moved Permanently
Location: https://example.com/new-path/resource
```

`301` は「永久移動」を意味します。
ブラウザはこのレスポンスを受け取ると、自動的に新しい URI へアクセスします。
検索エンジンも評価を引き継ぎます。

しかし、リダイレクトはあくまで応急処置です。
理想は最初から変わらない URI を設計することです。

---

## 5. クール URI の実践例

### ブログ記事の URI

```
悪い例（変わりやすい）:
/category/web/2026/04/20/title-of-post.html

良い例（変わらない）:
/posts/12345
/posts/title-of-post    （スラッグ方式。タイトル変更でも変えない）
```

### ユーザープロフィール

```
悪い例（変わりやすい）:
/user.asp?name=yamamoto&role=admin

良い例（変わらない）:
/users/yamamoto
/profiles/yamamoto
```

### API エンドポイント

```
悪い例（変わりやすい）:
/api/v1/fetchUserData.php?user_id=42

良い例（変わらない）:
/api/v1/users/42
```

---

## 6. クール URI と名前空間

URI を設計するとき、将来の拡張を考えた名前空間を作ることが大切です。

```
/api/v1/users        → API エンドポイント
/docs/users          → ドキュメント
/admin/users         → 管理画面

→ それぞれ独立した名前空間があれば干渉しない
```

---

## 7. クール URI のまとめ

クール URI を実現するためのルール：

```
1. 実装の詳細を含めない
   - ファイル拡張子（.php .html .asp）は除く
   - CGI パス（/cgi-bin/）は除く

2. 組織・分類の詳細を含めない
   - 部署名、カテゴリー名は含めない（変わりやすい）

3. 日付は慎重に使う
   - /news/2026/04/20/... は変えられないが冗長になる
   - 必要なければ ID のみで識別

4. 変わらないものだけを URI に含める
   - 変わらないのは「リソースの ID（通し番号）」と「リソースの種類（名前）」

5. URI を変える必要が生じたら 301 リダイレクトを使う
```

---

## まとめ

- クール URI = 変わらない URI
- URI が変わるとリンク切れ・SEO 低下・ユーザー体験悪化につながる
- 実装の詳細・組織構造・コンテンツ属性を URI に含めないことが大切
- やむを得ず URI を変更する場合は 301 リダイレクトで対処する
- 最初から「この URI は10年後も変わらないか」を意識して設計する
