# 第3章-05：認証

---

## 1. 認証と認可の違い

まず重要な用語を整理します。

| 用語 | 英語 | 意味 |
|------|------|------|
| 認証 | Authentication（AuthN）| 「誰であるか」を確認する |
| 認可 | Authorization（AuthZ）| 「何ができるか」を確認する |

```
認証：パスポートでのチェック → 「あなたは山本花子さんですね」
認可：チケットの確認 → 「あなたはビジネスクラスに乗れます」
```

認証が先に来て、その後に認可の処理が行われます。

---

## 2. HTTP の認証の仕組み

HTTP の認証は次のフローで行われます。

```
① クライアント → サーバー: リクエスト（認証情報なし）

② サーバー → クライアント: 401 Unauthorized
                            WWW-Authenticate: Basic realm="example"

③ クライアント → サーバー: リクエスト（認証情報付き）
                            Authorization: Basic dXNlcjpwYXNzd29yZA==

④ サーバー → クライアント: 200 OK（認証成功）
```

---

## 3. Basic 認証

最も基本的な HTTP 認証方式です。

### 仕組み

ユーザー名とパスワードを `ユーザー名:パスワード` の形式で結合し、
**Base64 エンコード** してヘッダーに含めます。

```
user:password
↓ Base64 エンコード
dXNlcjpwYXNzd29yZA==
```

```http
Authorization: Basic dXNlcjpwYXNzd29yZA==
```

### 注意点

Base64 は **エンコードであり暗号化ではありません**。
簡単にデコードできるため、平文でパスワードを送っているのと同じです。

```
echo "dXNlcjpwYXNzd29yZA==" | base64 -d
→ user:password  （復元できる）
```

そのため、Basic 認証は **必ず HTTPS と組み合わせる** 必要があります。

### 現在の使いどころ

- サーバー同士の内部 API 通信（外部に公開されない）
- 開発環境での簡易的なアクセス制御
- シンプルな管理画面

---

## 4. Digest 認証

Basic 認証のパスワード平文送信の問題を改善した方式です。

### 仕組み

パスワードを直接送らず、**ハッシュ値** を使って認証します。

```
① サーバーが「ノンス（nonce）」という乱数を送る
② クライアントが パスワード + nonce + リクエスト情報 をハッシュ化
③ ハッシュ値だけをサーバーに送る
④ サーバーが同じ計算をして照合する
```

パスワード自体は送信されないため、Basic 認証より安全です。
ただし、HTTPS が普及した現在は使われる機会が減っています。

---

## 5. Bearer 認証（トークン認証）

現代の Web API で最もよく使われる認証方式です。

### 仕組み

**トークン（Token）** という文字列を Authorization ヘッダーに含めます。

```http
Authorization: Bearer eyJhbGciOiJSUzI1NiJ9.eyJzdWIiOiI0MiJ9.abc123
```

トークンは事前にログイン等で取得しておきます。

```
① ユーザーがログイン
② サーバーがトークンを発行して返す
③ クライアントはトークンを保存しておく
④ 以降のリクエストでトークンをヘッダーに含める
⑤ サーバーはトークンを検証して認証を確認する
```

### JWT（JSON Web Token）

Bearer 認証でよく使われるトークン形式です。

```
eyJhbGciOiJSUzI1NiJ9.eyJzdWIiOiI0MiIsIm5hbWUiOiJLYXp1a2kifQ.abc123
     ↑ヘッダー（Base64）      ↑ペイロード（Base64）           ↑署名
```

3つのパートを `.` でつないだ構造です。

**ヘッダー**: アルゴリズム情報
```json
{"alg": "RS256", "typ": "JWT"}
```

**ペイロード**: 実際のデータ（ユーザー ID など）
```json
{"sub": "42", "name": "Kazuki", "exp": 1745596800}
```

**署名**: ヘッダー + ペイロードをサーバーの秘密鍵で署名したもの

JWT の特徴：
- サーバーがデータベースを確認しなくても、署名を検証するだけで認証できる
- ペイロードは Base64 なのでデコードすれば誰でも読める（機密情報を入れてはいけない）
- 署名があるので改ざんはできない
- 有効期限（`exp`）を設定することが重要

## 6. API キー認証

サービスの API を利用するために使われる認証方式です。

```http
X-API-Key: your-api-key-here
Authorization: ApiKey your-api-key-here
```

URL パラメーターに含める方法もあります。

```
https://api.example.com/data?api_key=your-api-key-here
```

ただし、URL に含めるとログに残るためセキュリティ上好ましくありません。

## 7. OAuth 2.0

**第三者のサービスに代わって** リソースへのアクセスを許可する仕組みです。

```
例：Twitter の情報を使ったアプリへのログイン（「Twitter でログイン」）

① ユーザーが「Twitter でログイン」をクリック
② アプリが Twitter の認証ページにリダイレクト
③ ユーザーが Twitter にログインして、アプリへのアクセスを許可
④ Twitter がアプリに「認可コード」を渡す
⑤ アプリが認可コードを使ってアクセストークンを取得
⑥ アプリはアクセストークンで Twitter API を呼び出せる
```

ポイント：ユーザーの Twitter パスワードをアプリに教えなくて済む。

### OAuth 2.0 の登場人物

| 役割 | 説明 | 例 |
|------|------|----|
| リソースオーナー | ユーザー本人 | あなた |
| クライアント | アクセスを要求するアプリ | 外部 Web アプリ |
| 認可サーバー | アクセスを許可する | Twitter の認証サーバー |
| リソースサーバー | 保護されたリソースを持つ | Twitter API |

---

## 8. OpenID Connect

OAuth 2.0 をベースにした **認証** のための規格です。
OAuth 2.0 は「認可」の規格で、「認証」には直接使えないため、
認証目的で使えるように拡張したものです。

```
「Google でログイン」は OpenID Connect を使っています。
→ ユーザーが Google で認証 → アプリにユーザー情報（ID・名前・メール）を渡す
```

## 9. セッション管理と Cookie

HTTP はステートレスなので、「ログイン状態」を維持するために
セッション管理が必要です。

### Cookie ベースのセッション

```
① ログイン成功
② サーバーがセッション ID を生成し、DB に保存
③ Set-Cookie ヘッダーでセッション ID をブラウザに送る
④ ブラウザは以降のリクエストで Cookie ヘッダーにセッション ID を付ける
⑤ サーバーはセッション ID を DB で照合してユーザーを特定
```

```http
（レスポンス）
Set-Cookie: session_id=abc123; HttpOnly; Secure; SameSite=Lax; Path=/

（次回以降のリクエスト）
Cookie: session_id=abc123
```

### Cookie の属性

| 属性 | 意味 |
|------|------|
| `HttpOnly` | JavaScript からアクセスできなくする（XSS 対策）|
| `Secure` | HTTPS のみで送信する |
| `SameSite=Lax` | クロスサイトリクエストでの Cookie 送信を制限（CSRF 対策）|
| `Domain` | Cookie を送信するドメインを指定 |
| `Path` | Cookie を送信するパスを指定 |
| `Max-Age` | Cookie の有効期間（秒）|

---

## まとめ

| 認証方式 | 概要 | 用途 |
|---------|------|------|
| Basic 認証 | ユーザー名:パスワードを Base64 | 簡易的な認証（HTTPS 必須）|
| Digest 認証 | パスワードのハッシュを送る | 現在はほぼ使われない |
| Bearer/JWT | トークンをヘッダーに付ける | 現代の Web API |
| API キー | 固定のキーを送る | サービス間連携 |
| OAuth 2.0 | 第三者サービスの認可 | SNS ログイン等 |
| OpenID Connect | OAuth 2.0 ベースの認証 | 「〇〇でログイン」|

- 認証（誰か）≠ 認可（何ができるか）
- Bearer + JWT が現代の主流
- Cookie の HttpOnly・Secure・SameSite はセキュリティに必須
